- **A — Cua components, C:** [trycua/cua](https://github.com/trycua/cua) distinguishes **Lume**, Apple Virtualization.framework macOS/Linux VMs on Apple Silicon; **Lumier**, Docker-compatible interface to Lume; **computer-server**, UI/code-execution service typically inside sandboxes; **cua-agent**, agent orchestration. Their sandbox architecture isolates a desktop; it does not inherently target existing host windows.

- **“cuadriver,” C:** The project’s name is **Cua Driver**, executable `cua-driver`, macOS bundle `CuaDriver.app`; originally Swift, now Rust with platform backends, CLI/MCP and SDK bindings ([source](https://github.com/trycua/cua/tree/main/libs/cua-driver), [migration evidence](https://github.com/trycua/cua/issues/1525)). Maintainers date its open-source release to **April 22, 2026**. It performs **in-place, per-window background automation**, including accessibility, screenshots and pixel input; macOS uses undocumented SkyLight activation handling plus process-directed events ([release/architecture](https://github.com/trycua/cua/blob/main/blog/computer-use-2-ai-engineer-worlds-fair.md)). Limits include Chromium pixel right-clicks, canvas/game HID requirements, minimized keyboard commits and off-Space SwiftUI accessibility loss ([limits](https://cua.ai/docs/reference/cua-driver/limits)). Linux’s optional nested `cua-compositor` is separately isolated and experimental; stock-Wayland raw targeting remains limited ([evidence ledger](https://github.com/trycua/cua/blob/main/libs/cua-driver/docs/action-support.md)).

- **B — UFO/UFO², C:** The [UFO² paper §4](https://arxiv.org/html/2504.14603v2#S4) explicitly specifies **Windows RDP loopback creating a distinct session on the same machine**, displayed in a movable PiP window, with separate input queues/device contexts. Applications launch inside that session; “replica” does not establish cloning existing live HWNDs. **Availability caveat:** [repository README](https://github.com/microsoft/UFO/blob/main/ufo/README.md) still says PiP “coming soon/in development”; the paper documents architecture, not a reproducible public implementation. **I:** ordinary `mstsc localhost` should not be assumed sufficient.

- **C — Agent projects:** **C:** [Anthropic reference](https://github.com/anthropics/claude-quickstarts/tree/main/computer-use-demo) uses Docker, Xvfb and xdotool: isolated X desktop. [Agent-S](https://github.com/simular-ai/Agent-S) executes PyAutoGUI actions/screenshots; [ScreenAgent](https://github.com/niuzaisheng/ScreenAgent) uses VNC, optionally a GUI container. **I:** host interference depends on whether that desktop is shared. [OS-Copilot](https://github.com/OS-Copilot/OS-Copilot) is an agent/tool framework, with no established background-input guarantee. **C:** [OmniParser](https://github.com/microsoft/OmniParser) parses screenshots, not input delivery. [OpenAI CUA API](https://developers.openai.com/tracks/building-agents#computer-use) delegates execution to your environment; [Operator](https://openai.com/index/introducing-operator/) used its own browser—neither establishes a public host-window injection implementation.

- **C — Libraries:** [cliclick](https://github.com/BlueM/cliclick), [PyAutoGUI](https://github.com/asweigart/pyautogui), [nut.js](https://github.com/nut-tree/nut.js), [robotjs](https://github.com/octalmage/robotjs): conventional desktop mouse/keyboard control. [Hammerspoon `event:post(app)`](https://www.hammerspoon.org/docs/hs.eventtap.event.html#post) supports application-directed events. [Playwright](https://playwright.dev/docs/input)/[CDP `Input.dispatchMouseEvent`](https://chromedevtools.github.io/devtools-protocol/tot/Input/#method-dispatchMouseEvent) targets browser content without OS cursor movement; **headed Chromium can still activate on macOS/Linux**, per [Cua’s validation](https://cua.ai/docs/concepts/browser-targeting-and-background-delivery).

- **D — macOS, C:** `CGEventPostToPid` plus `kCGMouseEventWindowUnderMousePointer`/`…ThatCanHandleThisEvent` fields **91/92** addresses process/window delivery; additional private window metadata and activation handling are implementation-dependent ([documented experiment](https://github.com/rlmsinclair/claude-on-second-display/blob/main/docs/pid-posting-research.md)). [`AXUIElementPerformAction`](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction) invokes exposed controls. ScreenCaptureKit `SCContentFilter(desktopIndependentWindow:)` captures occluded windows; minimized streams pause ([Apple](https://developer.apple.com/videos/play/wwdc2022/10155/)). [`CGVirtualDisplay`](https://github.com/xocialize/VirtualDisplayKit) is private display creation; **I:** another display alone does not isolate input.

- **D — Windows, C:** `PostMessage`/`SendMessage` deliver `WM_LBUTTONDOWN/UP`, client coordinates and key messages; they do not reproduce hardware state. [MaaFramework](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/en_us/2.4-ControlMethods.md)/[pywinauto](https://github.com/pywinauto/pywinauto/blob/master/pywinauto/controls/hwndwrapper.py) expose such routes; Chromium/raw-input surfaces may reject them. [UIPI](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew) blocks privilege crossings. [UIA Invoke](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementinginvoke) is semantic. AHK `ControlClick … "NA"` avoids activation; [`ControlSend`](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/ControlSend.htm) modifiers can interfere with foreground typing.

- **Windows capture/isolation, C:** [`PrintWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow) blocks synchronously; [`PW_RENDERFULLCONTENT`](https://webrtc.googlesource.com/src/+/f89110d67902e787f6745ad2b52f7f09fc808512/modules/desktop_capture/window_capturer_win.cc) improves some composited captures, not universally. WGC [`CreateForWindow(HWND)`](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow) handles occlusion. [`CreateDesktop`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw) creates a desktop; [`SwitchDesktop`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-switchdesktop) visibly activates it. [Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/) provides VM isolation.

- **D — Linux, C:** [`XSendEvent`](https://github.com/jordansissel/xdotool/blob/master/xdotool.pod#sendevent-notes) sets `send_event`; rejection is app/event-dependent—blanket GTK/Qt/Chrome rejection is unproven. [`XCompositeNameWindowPixmap`](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man3/Xcomposite.3.html) captures redirected backing storage. [Xvfb](https://xorg.freedesktop.org/archive/X11R7.0/doc/html/Xvfb.1.html), [Xephyr](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xephyr.1.html), [Xpra](https://github.com/Xpra-org/xpra) offer separate X environments. Wayland [virtual-pointer](https://wayland.app/protocols/wlr-virtual-pointer-unstable-v1)/[virtual-keyboard](https://wayland.app/protocols/virtual-keyboard-unstable-v1) emulate seat input, not arbitrary HWND-style targeting; [ydotool/uinput](https://github.com/ReimuNotMoe/ydotool) similarly injects devices. [AT-SPI2 `do_action`](https://docs.gtk.org/atspi2/iface.Action.html) targets accessible controls. **I:** nested [Cage](https://github.com/cage-kiosk/cage)/[Weston](https://wayland.pages.freedesktop.org/weston/toc/running-weston.html)/[Sway](https://github.com/swaywm/sway) can isolate agent input when injection stays inside the nested compositor.
