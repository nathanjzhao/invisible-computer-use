## Action-approval: Confirmations Policy, elicitation, on-disk allowlists

### What it is
How the system decides that a computer-use action needs a human OK before it runs. Codex splits this in two layers: a natural-language "Computer Use Confirmations Policy" that the agent model itself follows to gate risky side-effects (delete data, transmit sensitive data, financial transactions, CAPTCHA, etc.), plus a mechanical per-app gate in the JS runtime that elicits "Allow Computer Use to use <app>?" and persists the answer as an on-disk bundle-identifier allowlist. cua-driver instead ships a daemon-side capability/risk/consent engine: a fixed per-tool risk classification (R0-R4), three permission modes, an immutable launcher-approved capability manifest, and a trusted in-process consent broker. The two systems solve overlapping problems from opposite ends: Codex gates fine-grained UI side-effects in the agent prompt, cua gates coarse tool operations in the daemon.

### cua-driver
- Per-tool risk classification: `rust/crates/cua-driver-core/src/authorization.rs`, `enum RiskClass { R0..R4, Unclassified }` (line 51) and `fn classify_tool_call(tool, args)` (line 954) returning a `RiskAssessment { class, enforcement, operation_sensitive }`. This is a static tool/operation table (e.g. `browser_prepare` existing_profile = R2, isolated = R1; `page get_text` = R2; screenshot-to-file bumps a class), not a side-effect taxonomy. Unclassified tools are hard-denied (line 1134).
- Permission modes: `authorization.rs` `enum PermissionMode { Standard, Bounded(alias autonomous), Unrestricted }` (line 1210). `AdapterProfileBehavior::for_mode` (line 172) maps each adapter to `ModeBehavior { Allow, Deny, RequireGrant, AllowWithoutGrant }`. Unrestricted needs `--dangerously-bypass-approvals`; Bounded needs `--capability-manifest` (`PermissionModeError`, line 1228).
- Central gate: `authorization.rs` `authorize_tool_call_with_context` (line 1121) runs hard invariants -> policy allow/deny -> risk classify -> manifest decision. `enforce_hard_invariants` (line 1169) refuses tools that target the driver's own PID.
- Static allow/deny policy: `rust/crates/cua-driver-core/src/policy.rs`, `PolicyEngine`/`YamlPolicy`/`RegoPolicy`, `authorize_tool_call` (line 298), with an admin "managed" ceiling intersected with a user policy (`configured_managed_policy`, line 235). Tool-name allowlists only (`allowed_tools`, line 393); no per-app-bundle or side-effect concept.
- Trusted consent broker: `rust/crates/cua-driver-core/src/consent.rs`. `trait ProtectedConsentProvider` (line 63) with `request_consent(&ConsentRequest) -> ProviderDecision`, `enum ConsentAction { Accept, Decline, Cancel }` (line 27), `ApprovalBroker` (line 106), `ProtectedGrant` with `is_live`/`revoke` (line 70), TTL default 2 min (line 23). This is the seam a host uses to render an approval; cua explicitly "never requires the host to render a particular UI" (line 60-61). Grants are in-memory and revocable, not written to disk.
- Capability manifest (Bounded mode): `rust/crates/cua-driver-core/src/session_manifest.rs`, `struct SessionManifest` (line 32) with `allow`/`deny`/`ask` tool sets, `expires_unix_ms`, `idle_timeout`, and notably `applications: Vec<ApplicationGrant>` where `ApplicationGrant { bundle_id, executable, launch, all_windows, terminate }` (line 59). `enum ManifestDecision { Allow, Deny, Ask, Undeclared }` (line 24). This is the nearest analog to Codex's per-app allowlist, but it is immutable, launcher-selected and `--approve-capability-manifest`-approved at daemon startup (module doc lines 1-5), sha256-pinned, and cannot be edited by a runtime elicitation.
- Session authorization: `rust/crates/cua-driver-core/src/session_authorization.rs`, `EffectiveAuthorizationContext` (line 176), `SessionModeCeiling` (line 45), `SessionAuthorizationRegistry` (line 460). Binds mode + manifest + policy hashes to a connection; `is_expired`/idle enforcement lives here.
- macOS permissions: `rust/crates/platform-macos/src/permissions/{mod,gate,panel,status}.rs`. `gate.rs` is a first-launch TCC gate (Accessibility/Screen Recording via `x-apple.systempreferences:` panes, polling) - OS-level entitlements, a different axis from action approval.
- Absent: a natural-language per-action Confirmations Policy (grepped the corpus/spec and cua rust; no delete/transmit/financial/CAPTCHA side-effect taxonomy). Absent: any runtime elicitation string like "Allow ... to use <app>" and any disk-persisted bundle-id allowlist with session/always scopes (grep for `elicit`/`approvedBundle`/`allowlist`/`persist.*approv` across `crates` returns only telemetry capability-flags `elicitation_form`/`elicitation_url` in `telemetry.rs`/`protocol.rs`, MCP capability advertisement, not an approval store). The `sky_js` side has no policy logic beyond the app elicitation; the native service holds the allowlist.

### Delta
- Matches: both have a launcher/host-approved app-scope grant (Codex `AppApprovalStore` bundle-id list; cua `ApplicationGrant.bundle_id` in the capability manifest), both cancel on user-stop/idle (Codex `userStoppedSession`/`userIntervened`/`IdleTimeoutReached`; cua `ConsentAction::Cancel`, `EffectiveAuthorizationContext::is_expired`, manifest `idle_timeout`), and both hard-deny apps that org/safety policy forbids (Codex `denied`/`forbidden`/`appNotAllowed`; cua policy deny + `Unclassified` deny).
- cua-ahead: a real daemon-side enforcement engine (risk classes, three permission modes, admin ceiling intersected with user policy, sha256-pinned immutable manifest, in-process trusted consent broker with request-digest binding and revocation, self-PID hard invariant). Codex's policy layer is prompt text the model is trusted to obey; its mechanical gate is only per-app.
- Codex-ahead: the fine-grained side-effect Confirmations Policy (delete/transmit/financial/CAPTCHA/login/upload/software-install/system-settings/medical, plus the user-authored-vs-third-party-content trust taxonomy and sensitive-data transmission rules), and a live runtime elicitation that writes a persistent bundle-id allowlist with session vs always scopes to disk. cua has no notion of "confirm right before this specific side-effect," no third-party-content-is-not-consent rule, and no user-facing "always allow this app" that survives across sessions.

### Recreate / port plan
- Confirmations Policy (copy-verbatim as an agent policy doc). It is model-facing guidance, not driver code. Ship `computer-use-node-repl-guardian.md`'s policy section as an agent system-prompt/skill doc for whatever model drives cua. Hook point: the harness that composes the agent prompt, not the Rust daemon. Should we build this: yes if cua is ever paired with an autonomous agent doing web/UI side-effects; it is the single biggest safety gap. It is copy-verbatim because the taxonomy is provider-neutral. Caveat: it only works if the agent is trusted to follow it, so treat it as defense-in-depth layered on the daemon gate, never the sole control.
- Runtime elicitation + persistent bundle-id allowlist (thin-port onto the consent layer). Implement a `ProtectedConsentProvider` (consent.rs line 63) whose `request_consent` renders "Allow <app>?" via the host UI and returns Accept/Decline/Cancel, then persist accepted bundle ids. Add an app-scope resource kind and an on-disk store mirroring Codex: a per-session TOML (`[apps] allowed=[...]`) and a global JSON (`approvedBundleIdentifiers`) checked before app-targeting tools (`click`/`type_text`/`get_accessibility_tree`/`browser_prepare`, the process-targeting list at authorization.rs line 1178). Hook points: `authorize_tool_call_with_context` (line 1121) to add an app-allowlist check on the resource's `bundle_id`, `ApplicationGrant` (session_manifest.rs line 59) as the existing shape to reuse, and `ApprovalBroker`/`ProtectedGrant` (consent.rs) for the accept/persist/revoke lifecycle. Should we build this: partially. A persistent per-app allowlist is a genuine ergonomics win and fits cua's model cleanly. But scope it to a host/launcher-driven store; do not let the agent or tool arguments write it (cua's manifest doc, session_manifest.rs lines 1-5, is explicit that the agent may propose but only the launcher approves). The "session/always persist" split maps to cua's per-session context vs a process-global store. App-specific bits of Codex (the `2DC432GLL2` group container path, `CodexComputerUseIdleTimeoutReached` analytics, the SkyComputerUseService `AppApprovalStore` class) are non-goals; only the shape (bundle-id list + session/always scope) ports.

### Addendum: mandatory hard-deny layer + newer @oai/cua interface (verified against the Windows build)

Re-checked against the newer Windows MSIX corpus (`codex-corpus/windows/`, `@oai/sky` 0.6.26 + `@oai/cua` 0.2.4). Two additions, neither a new capability:

- Mandatory hard-deny list, distinct from the Confirmations Policy. `codex-corpus/windows/guidance.md` ships a "Non-negotiable Windows Automation Safety" section: "These denies are mandatory. Confirmation policy applies only to allowed-but-confirmed actions and cannot replace these denies." The denies: no terminal apps or Run dialog or embedded PowerShell/.bat, no authentication dialogs, no password managers, no security/anti-malware apps, no automating the ChatGPT/Codex UI itself, no Windows/Meta key or `press_key` with Meta/Win/Super/Cmd/OS, no age verification, plus untrusted-content and read-vs-transmit rules. This is a hard allow/deny layer ABOVE the four confirmation modes. Port: copy-verbatim as agent policy, same hook point as the Confirmations Policy. The macOS guardian carries the confirmation modes; this platform-scoped hard-deny list is the newer packaging's addition.
- `@oai/cua` unified interface. The `unified-computer-use` plugin exposes a single `cua` API (`cua.getState()`, `cua.getApp(name)`) that merges native-app control, browser control, and tabs into one persistent JS session, succeeding the split `sky` (computer) + browser surfaces. This is an interface evolution of capabilities already covered here and in sections 01, 06, 07, and 13, not a new capability. If we build a unified facade over cua-driver, this `getState`/`getApp` shape is the model to match. cua-driver already spans native + browser tools under one MCP server (section 13), so the gap is a thin unifying wrapper, not new mechanism.
