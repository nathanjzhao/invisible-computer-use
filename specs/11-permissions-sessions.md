## Permission modes, capability manifests, session lifecycle, locked screen

### What it is
The authorization subsystem decides, per tool call, whether an operation is inside the configured ceiling and whether it also needs human consent, then scopes that decision to a session that can be revoked. In cua-driver this is a layered, deny-by-default model with three permission modes, a narrow-only capability manifest, a trusted consent broker, and a macOS TCC onboarding gate. In Codex/Sky the equivalent is much thinner: a per-app bundle-id allow/deny/forbid check resolved by the native service, plus a large macOS-specific lock-screen auto-unlock subsystem that cua-driver has no analogue for and that we should not reproduce.

### Codex/Sky
Codex's runtime authorization is a per-app policy keyed on the target app's bundle identifier, resolved over IPC by the native service, with an enterprise and a safety verdict. The only permission-mode signal in the shipped code is a UI-level composer mode surfaced through analytics, not a three-tier enforced model. Separately, the native service ships a full macOS lock-screen guardian that can auto-unlock the login screen through an installed SecurityAgent authorization plugin.

- `dist/project/cua/sky_js/src/targets/mac/computer-use-policy.js` and `computer-use-policy.d.ts` — `withComputerUsePolicy(toolName, {app}, operation)` wraps every app-targeting tool. It calls `getAppPolicy(s.app)`, reads `v.target.bundleIdentifier`, then switches on `decision`: `"allowed"` returns the target; `"denied"` throws `Computer Use is blocked from using the app '<app>' by your organization's policy.`; `"forbidden"` throws `Computer Use is not allowed to use the app '<app>' for safety reasons.`. So policy is per bundle id, with an org/enterprise layer and an OpenAI safety layer. CONFIRMED.
- `Codex Computer Use.app/Contents/MacOS/SkyComputerUseService` (strings) — IPC message types `ComputerUseIPCAppPolicyRequest`, `ComputerUseIPCAppPolicyResult`, `ComputerUseIPCAppPolicyDecision`; verdict strings `Access forbidden`, `' by your organization's policy.`, `Computer Use is not allowed to use the app '`; enterprise keys `organizationID` / `organization_id`; an override symbol `ComputerUseAllowForbiddenTargets`. The bundle-id policy is decided native-side, not in JS. CONFIRMED.
- `SkyComputerUseService` (strings) — permission-mode surface is `AnalyticsEvents_V1_CodexComposerPermissionsModeChanged` / protobuf `protobuf_analytics_events.v1.CodexComposerPermissionsModeChanged`. This is a composer UI mode-change event, not an enforced standard/bounded/unrestricted ceiling. INFERRED (no enforced mode enum found in strings; searched the binary and sky_js).
- `SkyComputerUseService` (strings) — lock-screen subsystem classes: `SystemLockScreenMonitor`, `LockScreenGuardianCoordinator`, `LockScreenAutoUnlockCoordinator`, `SystemLockScreenController`, `SystemLockScreenOverlayPresenter`, `SystemLockScreenPhysicalInputMonitor`, `LockScreenLoginAuthorizationBroker`/`Attempt`/`SocketServer`, `CUALockScreenGuardianClient`; XPC `SAILockScreenGuardianXPCProtocol`; system notifications `com.apple.sessionagent.screenLockUIIsShown` and `com.apple.screenLockUIIsShown`; unix socket `/tmp/com.openai.sky.CUAService/LockScreenLoginAuthorization.sock`; guardian app `CUALockScreenGuardian.app`. A physical-input monitor exists to bail out of auto-unlock when a human uses the machine. CONFIRMED.
- `/Library/Security/SecurityAgentPlugins/CodexComputerUseAuthorizationPlugin.bundle` — root-owned SecurityAgent authorization plugin, `Contents/MacOS/CodexComputerUseAuthorizationPlugin` (70 KB), `Info.plist` bundle id `com.openai.sky.CUAService.AuthorizationPlugin`, `CFBundleVersion 799`, `LSMinimumSystemVersion 14.4`, installed by `Codex Computer Use Installer.app`. This plugin participates in the macOS login/unlock authorization mechanism so the agent can drive a locked machine. CONFIRMED.

### cua-driver
cua-driver splits authorization into orthogonal layers, all frozen at trusted daemon startup and never settable by a tool argument: a permission mode, a capability policy ceiling, a per-adapter risk map, an optional narrow-only capability manifest, a request-bound consent broker, and a session lifecycle with revocation. There is no lock-screen or login-authorization concept anywhere in the tree.

- `rust/crates/cua-driver-core/src/authorization.rs` — `enum PermissionMode { Standard, Bounded, Unrestricted }` (`autonomous`/`yolo` aliases), resolved once via `configured_permission_mode()` from `CUA_DRIVER_PERMISSION_MODE`. `parse_permission_mode` requires `CUA_DRIVER_DANGEROUSLY_BYPASS_APPROVALS` for unrestricted; `validate_startup_authorization` enforces bounded-needs-manifest, manifest-needs-approval, and `CUA_DRIVER_DISABLE_UNRESTRICTED` admin lockout. `ENFORCEMENT_ADAPTERS` is the static risk map: `RiskClass` R0-R4, per-adapter `scope_keys`, `idle_ttl_seconds`/`absolute_ttl_seconds`, and `AdapterProfileBehavior::for_mode` -> `ModeBehavior {Allow, Deny, RequireGrant, AllowWithoutGrant}`. `authorize_tool_call_with_context` runs hard invariants, capability policy, risk classification, then manifest decision. This is the core mechanism.
- `rust/crates/cua-driver-core/src/policy.rs` — the capability ceiling: `authorize_tool_call` intersects a managed layer (`CUA_DRIVER_MANAGED_POLICY_FILE`, immutable admin ceiling) with a user layer (`CUA_DRIVER_POLICY_FILE`). `PolicyEngine` is `Yaml` or `Rego`, deny-by-default, content-hashed (`policy_sha256`); a user layer can only narrow, never widen, the managed layer. This is where an app allow/deny list would live.
- `rust/crates/cua-driver-core/src/session_manifest.rs` — `SessionManifest` (`load_manifest`, `CUA_DRIVER_CAPABILITY_MANIFEST_FILE` + `..._APPROVED`), YAML versions 1-3, narrow-only. Resources include `apps` with `bundle_id` or `executable` identity plus `terminate` grant (`ApplicationGrant`, `TerminationGrant`), browser `existing_profiles`/`origins`/`profiles`, desktop `windows`/`applications`/`display`, file `read`/`write` exact paths and directory roots, `processes.terminate`, `driver_configuration.changes`, `computer_history.operations`. `decision()` gives Allow/Deny/Ask/Undeclared; `authorize_protected_resource` matches implementation-attested resources; `sha256`, `expires_after` (<=24h), terminal `idle_timeout`. This is cua's structural analogue to Codex's bundle-id policy, and far richer.
- `rust/crates/cua-driver-core/src/consent.rs` — `ProtectedConsentProvider` trait is the trusted-host seam; `ApprovalBroker::request_bound` mints a digest-bound `ConsentRequest`; `ProtectedResourceGrants::authorize` returns a revocable `ProtectedGrant` keyed by `digest_resource` + session, with idle/absolute TTL; `revoke_session`/`revoke_resource`/`revoke_all`. Digest mismatch or expiry fails closed. No UI is mandated.
- `rust/crates/cua-driver-core/src/session_authorization.rs` — `SessionModeCeiling` (immutable allowed modes, unrestricted-acknowledged, TTLs, policy hashes) and `EffectiveAuthorizationContext` bound to an opaque, non-serializable `AuthenticatedActionConnection`. Per-session mode delegation (`bind_delegated_session`) exists but `status_json` reports `session_mode_delegation_ready: false` / blocker `authenticated_action_connection_required`; live calls use `legacy_context()` = process mode. Per-session revoke: `revoke_connection`, `revoke_host`, `revoke_all`.
- `rust/crates/cua-driver-core/src/session.rs` and `session_tools.rs` — lifecycle records with `SessionDispatchGuard`, idle sweep `evict_idle` (`DEFAULT_SESSION_IDLE_TTL` 5 min), tombstones `ended_sessions`, cleanup hooks (cursor overlay remove, recording stop), owner-checked `revive_session_for_owner`, `revoke_all_sessions`, and the terminal `suspend_runtime_scope` latch. `start_session`/`end_session`/`escalate_session` tools accept only the public `session` label.
- `rust/crates/cua-driver-core/src/authorization.rs` (launch grants) — `configure_launch_grants` accepts only `existing-profile`; `--grant existing-profile` is valid only in standard mode (`rust/crates/cua-driver/src/main.rs:89`, `cli.rs:666`), is process-local, and is never read from env or tool args. It pre-authorizes existing-profile Chromium attachment so standard mode needs no per-attach consent.
- `rust/crates/platform-macos/src/permissions/{mod,gate,status,panel}.rs` — TCC onboarding. `MissingPermission { Accessibility, ScreenRecording }`; `gate::run_if_needed` inspects TCC, raises the system prompts, opens `x-apple.systempreferences:...Privacy_Accessibility` / `...Privacy_ScreenCapture`, and polls until green. Surfaces: native `NSPanel` (`panel.rs`) or terminal banner. Opt-out `--no-permissions-gate` / `CUA_DRIVER_RS_PERMISSIONS_GATE=0`. `status.rs` gives the raw booleans. No lock-screen or login-auth handling exists (grep for lockscreen/securityagent/auto-unlock returns only app-name filters for `loginwindow`).

### Delta
| Dimension | Codex/Sky | cua-driver |
|---|---|---|
| Permission modes | UI composer mode only, not an enforced ceiling | Enforced Standard/Bounded/Unrestricted, startup-frozen, mode never widens policy |
| App gating | Per bundle-id allow/denied/forbidden via native IPC, org + safety layers | No first-class bundle-id verdict; app identity lives in the manifest `apps[]` and could feed managed policy |
| Capability manifest | None; a single per-app decision | Rich narrow-only YAML manifest: apps, windows, origins, files, processes, config, TTLs, sha256 |
| Consent / grants | Accept/cancel/decline prompt flow, org policy | Digest-bound `ApprovalBroker` + revocable `ProtectedResourceGrants` with idle/absolute TTL |
| Revocation | Not evident in shipped surface | Per-resource, per-session, per-connection, per-host, revoke-all, terminal runtime latch |
| TCC onboarding | Native flow inside the service | Explicit `gate`/`panel` with poll loop, System Settings deep links, headless opt-out |
| Locked-screen operation | Full guardian + auto-unlock + root SecurityAgentPlugin | None, deliberately |

Net: cua-driver is ahead on modes, manifest, consent, and revocation. Codex is ahead only on (1) the per-bundle-id enterprise/safety app gate and (2) operating a locked machine.

### Recreate/port plan
1. Per-app bundle-id gate. thin-port. Reuse the existing managed policy layer in `policy.rs`: add an app-identity rule form (deny/forbid by `bundle_id` or `executable`) evaluated in `authorize_tool_call_with_context` before dispatch, mirroring Codex's `allowed`/`denied`/`forbidden`. The manifest `resources.apps[]` in `session_manifest.rs` already carries bundle-id and executable identity, so the allow side is present; only the managed deny/forbid verdict needs adding.
2. Enterprise/org provenance. native-patch. cua already hashes and reports the managed policy (`managed_policy_sha256`, `managed_policy_source`); wire an org identifier into `status_json` and into the managed ceiling so the "blocked by your organization's policy" verdict has the same provenance as Codex's `organization_id`.
3. Built-in safety forbidden list. thin-port. Encode Codex's "forbidden for safety reasons" set as a built-in managed ceiling entry with a distinct refusal code, matching Codex's `ComputerUseAllowForbiddenTargets` as a trusted-startup override only.
4. Permission-mode parity. copy-verbatim (no code). Map the Codex composer mode onto cua's existing `--permission-mode` at the launcher; no driver change is required.
5. Locked-screen guardian and SecurityAgentPlugin. do not copy. The `LockScreen*` guardian, `LockScreenAutoUnlockCoordinator`, the `LockScreenLoginAuthorization` socket, and especially `/Library/Security/SecurityAgentPlugins/CodexComputerUseAuthorizationPlugin.bundle` require a root-installed authorization-database plugin that can unlock the login screen. This is an OpenAI-signed, high-blast-radius component outside the cua-driver trust model; exclude it from any port and keep cua-driver's contract of operating only an unlocked, TCC-authorized desktop.
