## Audio and media capture

Codex/Sky exposes computer-audio recording as a first-class, opt-in tool pair (`start_audio_recording` / `stop_audio_recording`) that captures the machine's audio output for a bounded duration and returns a WAV as a data URL. It is gated behind the `SKY_ENABLE_AUDIO=1` env var and a separate high-risk approval, and is implemented natively on mac (Swift service over IPC) versus ffmpeg+PulseAudio on linux. cua-driver records screen video and action trajectories and bundles an ffmpeg installer, but has no audio/microphone/media-capture path at all; it only carries a governance placeholder that is explicitly not exposed.

### Codex/Sky (CONFIRMED)

- Tool source, mac: `.../sky_js/src/targets/mac/audio_recording.js` exports `start_audio_recording` / `stop_audio_recording`. `start` reads `max_duration_ms` (default `6e4` = 60000 ms), validates it is an integer `100..300000` (constants `s=100`, `c=3e5`) or throws "audio recording duration must be an integer from 100 through 300000", then `yield u()` (the approval), then `getClient().startAudioRecording({maxDurationMilliseconds})`. `stop` requires the service to return a `file:` URL (throws otherwise), converts it to `{filepath, bytes, data_url}` with `to_data_url(..., "audio/wav")`.
- Tool source, linux: `.../sky_js/src/targets/linux/audio_recording.js` exports `create_audio_recording`. Same bounds (`c=100`, `a=3e5`, default `6e4`, error "max_duration_ms must be an integer from 100 through 300000"). It runs `pactl get-default-sink`, then spawns `ffmpeg -hide_banner -loglevel error -y -progress pipe:2 -f pulse -i ${sink}.monitor -t <sec> -ar 24000 -ac 2 -c:a pcm_s16le recording.wav` into a `sky-audio-` tmpdir; it waits for `progress=continue` before resolving, and `stop` writes `q\n` to ffmpeg stdin, awaits close, and returns `{filepath, bytes, data_url}` audio/wav. Note this records `${sink}.monitor` (the output loopback), i.e. system/desktop audio, not the mic.
- Feature gate: `.../targets/mac/create_client.js` and `.../targets/linux/create_client.js` both add the audio methods only when `"1"===process.env.SKY_ENABLE_AUDIO`; otherwise the client omits them entirely (mac spreads `...?{start_audio_recording,stop_audio_recording}:{}`; linux `Object.assign(g, t(_))` only under the same check). Off by default.
- Separate high-risk approval: `.../targets/mac/computer-use-policy.js` exports `requestComputerAudioApproval` (fn `p`), which calls `createElicitation` with message "Allow Computer Use to record computer audio?", `riskLevel:"high"`, `persist:["session"]`, `tool_name:"start_audio_recording"`, and throws "Computer Use was not approved to record computer audio" on non-`accept`. This is distinct from the per-app approval `withComputerUsePolicy` ("Allow Computer Use to use ...") in the same file, and its persistence is session-only (no "always").
- Native mac backend (CONFIRMED via `strings` on `SkyComputerUseService`): symbols `ComputerUseAudioRecorder` / mangled `_TtC11ComputerUse24ComputerUseAudioRecorder`, plus IPC message types `ComputerUseIPCStartAudioRecordingRequest` and `ComputerUseIPCStopAudioRecordingRequest`. So mac capture is done by the Swift service, not ffmpeg. (The many `CODEX_REALTIME_VOICE_..._MICROPHONE_...` strings are a separate realtime-voice mic subsystem, not this computer-audio recorder.)
- RPC plumbing: `.../sky_js/src/service.js` (`handleRpc`) and `.../sky.js` special-case `stop_audio_recording` to strip the payload to `{filepath, data_url}` across the boundary (fn `d`), and `sky.js` rehydrates `bytes` from the base64 data URL on the client side (fn `a`). `start_audio_recording` routes through the generic `execute` path.

### cua-driver (audio: absent)

- No audio capture anywhere. A strict grep `audio_recording|record_audio|AudioRecorder|microphone|startAudioRecording` over `rust/crates` returns a single hit, in `authorization.rs` (below). The broad `audio|microphone|pulse` hits are all unrelated `ClickPulse` cursor-overlay animation commands (e.g. `platform-linux/src/tools/impl_.rs`, `cursor-overlay/src/lib.rs`).
- Media recording that does exist is video/screen + action-trajectory only: `cua-driver-core/src/recording.rs` (~85k), `action_record.rs` (~70k), `recording_render.rs`, `recording_zoom.rs`, `recording_tools.rs`, `recording_loader.rs`, `video.rs`, `video_ffmpeg.rs`, `ffmpeg_install.rs`. `video_ffmpeg.rs` and `video.rs` contain no audio flags (`-f pulse`, `-i` audio input, `pcm`, `.wav`, `-ac`); `ffmpeg_install.rs` provisions ffmpeg for the video pipeline.
- Governance stub only: `cua-driver-core/src/authorization.rs` (~line 624) defines `EnforcementAdapterDescriptor { id: "devices", operations: &["microphone", "camera"], state: RiskEnforcement::NotExposed, risk_class: RiskClass::Unclassified, resource_kind: "device_capture", authorization_requirement: "required_before_exposure", authorization_source: "capability_not_exposed", profile_behavior: AdapterProfileBehavior::Denied, ... }`. So cua reserves a mic/camera capture slot in its authorization model but deliberately does not expose or implement it.

### Delta

- Matches: both projects wrap ffmpeg for media capture (cua for video; Sky-linux for audio) and both provision/expect ffmpeg. Both gate capture behind an approval/authorization layer (Sky's high-risk elicitation; cua's enforcement adapters).
- Codex-ahead: audio capture as a shipped tool pair, native mac recorder over Swift IPC, a dedicated high-risk session-only approval, duration bounds (100..300000 ms, default 60000), and WAV-as-data-url return. cua has none of this.
- cua-ahead: far richer video/screen recording plus action-trajectory recording, render, and zoom (Sky's shipped JS has no video recorder here), an in-tree ffmpeg installer, and an authorization engine that already models `device_capture` as an adapter (denied by default) if it were ever enabled.

### Recreate / port plan and "should we build this"

- Hook points if pursued: (1) flip the existing `authorization.rs` "devices" adapter from `RiskEnforcement::NotExposed` / `AdapterProfileBehavior::Denied` to an active, manifest-gated, high-risk grant mirroring Sky's `persist:["session"]` elicitation; (2) linux is a near-thin-port of `linux/audio_recording.js` reusing the ffmpeg dependency already installed (`pactl get-default-sink` -> `ffmpeg -f pulse -i <sink>.monitor ... pcm_s16le`), returning a WAV path/bytes; (3) mac has no cheap path (Sky uses a native Swift `ComputerUseAudioRecorder`), so parity means new native code in `platform-macos` using ScreenCaptureKit/CoreAudio (system audio) or AVFoundation, which is the bulk of the effort; (4) surface `start_audio_recording` / `stop_audio_recording` with the same 100..300000 ms bounds behind an env/manifest flag equivalent to `SKY_ENABLE_AUDIO`.
- Honest call: this is a non-goal for a generic CUA driver. Audio recording is app-specific to the Codex product's turn model (capture computer audio for one bounded action), it is off by default even in Codex, and cua's own authorization model already classes device capture as capability-not-exposed / denied. A generic driver's media remit is screen + action-trajectory recording, which cua already does better than Sky's shipped JS. Build it only if a downstream product explicitly needs turn-scoped desktop-audio capture, and even then linux-only (thin) before paying for the mac native recorder.
