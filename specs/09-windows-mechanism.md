## Windows mechanism: UIA + SendInput + WGC + PiP

### 1. What it is

The Windows actuation stack: how each system reads a window's control tree (UI Automation), performs semantic actions (UIA InvokePattern / ValuePattern), synthesizes raw input (SendInput / PostMessage / pointer injection), and screenshots a specific window even when another window covers it (Windows.Graphics.Capture). The decisive axis is whether input is delivered to the *active desktop* by fronting the target, or *in the background* without ever raising it. Picture-in-picture (PiP) is the optional floating preview that mirrors the last post-action screenshot.

### 3. cua-driver

cua implements the full stack natively in Rust, and inverts Sky's default: background/no-foreground first, foreground only on explicit opt-in.

- `rust/crates/platform-windows/src/uia/mod.rs` — UIA tree via `IUIAutomation` COM + one batched `IUIAutomationCacheRequest` (`walk_tree_bounded`, `walk_cached_bounded`). `detect_cached_actions` maps patterns to actions: `InvokePattern`->invoke, `TogglePattern`->toggle, `SelectionItemPattern`->select, `ExpandCollapsePattern`->expand, `Value`/`RangeValuePattern`->set_value, `ScrollPattern`->scroll, `TextPattern`->text. `invoke_menu_element` calls `IUIAutomationInvokePattern::Invoke`, `ExpandCollapsePattern::Expand`, `SelectionItemPattern::Select`; `invoke_menu_path` re-walks fresh state per hop. CoreWindow UWP fallback (`walk_root_by_pid`) and SAL/VCL MSAA fallback.
- `rust/crates/platform-windows/src/uia/fg_bypass.rs` — `run_with_uwp_bypass` / `DisabledHwndGuard`: `EnableWindow(host,FALSE)` shield around UIA Invoke so XAML/UWP and Chromium hosts cannot self-`SetForegroundWindow` during the pattern call, while the Invoke still lands over the accessibility channel (0/507 z-drops measured). Known gap: WPF `UIElement.Focus()` still fronts, mitigated only by the UIAccess worker.
- `rust/crates/platform-windows/src/uia/scroll.rs` — `ScrollItemPattern::ScrollIntoView` then ancestor `ScrollPattern::Scroll`.
- `rust/crates/platform-windows/src/input/inject.rs` — the background actuator with NO foreground swap and no cursor move: `inject_click_screen` / `inject_drag_screen` via `CreateSyntheticPointerDevice` + `InjectSyntheticPointerInput` (synthetic pen for clicks, standing touch digitizer `TOUCH_DEV` for drags). `NoActivateGuard` (WS_EX_NOACTIVATE) blocks click-activation; `target_visible_at_point` refuses an occluded target rather than raising it; `force_foreground_attached` re-asserts the user's prior foreground.
- `rust/crates/platform-windows/src/input/mouse.rs` / `input/keyboard.rs` — dual paths. Background: `post_click` / `post_char` / `post_key` (PostMessage). Foreground: `send_click_synthesized` (SendInput `MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_VIRTUALDESK` + brief `SetForegroundWindow` swap), `send_key_synthesized` / `send_text_synthesized` (SendInput `KEYEVENTF_UNICODE`/scancode, restore previous foreground). `is_chromium_target_window` (`Chrome_WidgetWin_`).
- `rust/crates/platform-windows/src/input/delivery.rs` — `DeliveryMode` (`Background` default vs `Foreground`), `would_be_silently_dropped(hwnd, EventKind)` per-framework matrix (Chromium, WPF `HwndWrapper`, GTK `gdkWindow/Surface`, VCL `SAL`, Tk, WinUI3), and `background_unavailable_error` structured refusal with a `foreground` escalation hint.
- `rust/crates/platform-windows/src/input/mod.rs` — `post_message_blocked_by_uipi`: integrity-level check so posting to a higher-integrity window fails loudly instead of silently.
- `rust/crates/platform-windows/src/wgc.rs` — `screenshot_window_via_wgc`: `Direct3D11CaptureFramePool::CreateFreeThreaded` + `IGraphicsCaptureItemInterop::CreateForWindow`, `SetIsBorderRequired(false)`, `SetIsCursorCaptureEnabled(false)`, polls `TryGetNextFrame` (1500 ms). This is the occlusion-immune per-window capture.
- `rust/crates/platform-windows/src/capture.rs` — capture routing: `PrintWindow(PW_RENDERFULLCONTENT)` -> `is_mostly_black_bgra` sentinel -> WGC -> screen-region `BitBlt`; XAML/UWP hosts (`is_xaml_host_hwnd`) route WGC first; `target_is_obscured` flags occluded BitBlt results.
- `rust/crates/cua-driver-uia/src/{lib.rs,main.rs}` — the `uiAccess=true` worker on `\\.\pipe\cua-driver-uia`, so UIA activations and `SetForegroundWindow` swaps a non-UIAccess daemon cannot perform get routed through an elevated helper. Authorization by `authorized_parent_pid` + owner SID (`client_identity_is_authorized`).
- `rust/crates/platform-windows/src/virtualdesk.rs` — `to_virtualdesk_absolute`: multi-monitor normalization for `MOUSEEVENTF_VIRTUALDESK` (negative-origin layouts). NOTE: this is coordinate math, NOT a hidden/secondary Win32 desktop. No `CreateDesktop`-style off-screen desktop input path was found in this crate.
- PiP on Windows is NOT implemented: `rust/crates/platform-windows/src/pip/mod.rs` `WindowsPipBackendFactory::start` returns `Err("PiP preview is not yet implemented on Windows")`. The cross-platform plumbing exists in `rust/crates/cua-driver-core/src/pip_hook.rs` (`push_pip_frame`) and the `pip-preview` crate; only `platform-macos/src/pip/mod.rs` (floating non-activating NSWindow) implements a backend.
- The `winrects@cua` helper the task pointed at (`wayland-helper/winrects@cua/extension.js`) is a Linux/GNOME Shell extension (`org.cua.WinRects` D-Bus: `GetRects`/`Capture`/`Activate`), not a Windows component. No Windows analogue by that name.

### 5. Recreate/port plan

Goal: reproduce Codex/Sky's active-desktop Windows behavior on cua-driver. The native primitives (UIA, SendInput, WGC) already exist and are arguably ahead, so this is mostly a default/profile change, not new native code.

1. copy-verbatim: vendor `codex-corpus/mac/skills/windows-SKILL.md` and `docs/sky-window2-api.md` as the behavioral contract and tool-surface reference for the cua Windows tools. No code.
2. thin-port: add an "active-desktop profile" that makes cua match Sky's model. In `rust/crates/platform-windows/src/input/delivery.rs`, default `DeliveryMode` to `Foreground` under the profile (or have the agent/adapter pass `delivery_mode:"foreground"` and call `activate_window` first). cua already has `send_click_synthesized` / `send_key_synthesized` / `send_text_synthesized` + activation, so this is wiring, not new actuators. This alone reproduces Sky's "activate then SendInput" reach into Chromium/WPF/GTK.
3. thin-port: map the window2 verbs onto cua tools 1:1 (`perform_secondary_action` -> UIA secondary actions in `uia/mod.rs`; `set_value` -> ValuePattern; `get_window_state` include_screenshot/include_text already present). Confirm the tool names/args match `sky-window2-api.md`.
4. native-patch (only for flash-free parity): route Chromium/WPF activations through the existing `cua-driver-uia` UIAccess worker so foreground swaps succeed silently, instead of the visible SetForegroundWindow flash. The worker and pipe already exist; this is enabling and wiring, not new IPC.
5. large-build (optional, only if a Windows PiP is required): implement `WindowsPipBackendFactory::start` in `platform-windows/src/pip/mod.rs` per its own TODO (layered `WS_EX_NOACTIVATE | WS_EX_TOPMOST` HWND fed by `pip_hook::push_pip_frame`). Not needed to match Codex's core Windows behavior.

### 6. Live measurement (cua-driver 0.24.1 on Windows Server 2022, this run)

STATUS: LIVE-MEASURED (run 1 = delivery; run 2 = focus oracle). Everything above the delta table was static (a teardown of the Codex binary, plus reading cua's Rust source). This section is the first time cua-driver's Windows stack was actually run. Full scoreboard and artifacts: `win-eval/parity-scoreboard.md`, `win-eval/results.json`. EC2 interactive console session (autologon Administrator, logon scheduled task, because UIA/SendInput need session 1 and SSM runs as SYSTEM in session 0). Target is a WinForms fixture with a button + textbox logging receiver events.

> CORRECTION + RESOLUTION (2026-09-09, after adversarial review). Run 1 proved DELIVERY but had no focus oracle and the target was actually frontmost (the fixture self-`Activate()`d), so it could not establish "invisible." Run 2 (`win-eval2/parity-scoreboard.md`, `eval6-oracles.json`, `fx6.log`) fixes this with a real oracle: `GetForegroundWindow` before/after every action PLUS the fixture logging its own `focused` state. On a VISIBLE, NON-FOREGROUND target (foreground held by a different window 327936 throughout; the fixture logged `deactivated`), UIA `click` (InvokePattern) fired `buttonPressed` with `focused:false` and UIA `set_value` (ValuePattern) landed `textChanged` with `focused:false`, and neither raised the window (`target_fg_after=false`). `type_text` (SendInput) escalated `delivery_failed`→foreground, could not foreground, and did not deliver. Separately, on a MINIMIZED target, cua `click` returns an honest `window_minimized` refusal (off-screen coordinate guard) while `set_value` still lands. So the "cua background rung" claim is now oracle-confirmed for a visible-unfocused window, matching the macOS/Linux focus oracles.

Permissions probe: `elevated=true`, `integrity_level=High`, `post_message=true`, `uia=true`. The window enumeration includes cua's own `Cua.AgentCursorOverlay.default` overlay window, so the Windows ghost cursor (delta-table row) is live-confirmed as a real separate overlay, not just source.

Action matrix, driver response verified against the fixture's own receiver log (the driver reports `effect: unverifiable` for every Windows action, so the fixture log is the oracle, exactly as the macOS click proof was):

| action | driver route | driver delivery | fixture-log oracle | invisible? |
| --- | --- | --- | --- | --- |
| click (button) | `accessibility` (UIA InvokePattern) | background | `buttonPressed` on target pid | YES, focus-free |
| set_value (textbox) | `accessibility` (UIA ValuePattern) | unknown | `textChanged`="hello windows" on target pid | YES, focus-free |
| type_text | `synthetic_events` (SendInput) | background then escalation `{reason: delivery_failed, target: foreground}` | no extra event | NO, escalates to foreground |

This shows, at the code-behavior level: UIA InvokePattern/ValuePattern deliver while the target is not the foreground window and without raising it (run 2's `focused:false` + `GetForegroundWindow` oracle) — cua's background rung, which Sky's activate-then-SendInput model does not do — while raw SendInput synthesis is bound to the active desktop and self-reports `delivery_failed` then escalates to foreground. That escalation is exactly Sky's active-desktop model. So the two systems agree on the raw-input path and diverge only on whether a semantic UIA background rung exists (cua yes, Sky no). The cross-OS synthesis (macOS AX / Windows UIA / Linux AT-SPI all deliver focus-free; CGEvent-mouse / SendInput / XTest all need the active desktop) is in `win-eval/parity-scoreboard.md`.
