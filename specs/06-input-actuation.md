## Input actuation: AX actions vs pixel

### What it is
The layer that turns a tool call (click, type, scroll, drag, menu, key) into real macOS input. Both Codex/Sky and cua-driver use the same two-rung design: an **AX rung** that drives one cached element by accessibility RPC (`AXUIElementPerformAction` / `AXUIElementSetAttributeValue`), and a **pixel rung** that synthesizes CGEvent/NSEvent mouse and key events and posts them to the target pid. AX is primary because it hit-tests semantically and works on backgrounded/hidden windows; the pixel rung is the fallback for canvas/WebGL/custom surfaces the AX tree does not expose. The two systems are near-identical here because cua-driver is a Rust port of the Swift service, its tool docstrings say so verbatim ("matches the Swift reference ClickTool.swift").

### Codex/Sky
The JS SDK is a paper-thin forwarder; all actuation lives in the native `SkyComputerUseService` Swift binary, reached over an IPC pipe.

- `codex-corpus/mac/skills/macos-SKILL.md` — the actuation policy the model is told to follow: "Prefer `element_index`-based actions over coordinate actions whenever an accessibility element is available. If AX actions are not available or not working, fall back to using screenshots and coordinate clicks." Documents the tool surface: `click`, `type_text`, `scroll`, `set_value`, `press_key`, `select_text`, `perform_secondary_action`, `drag`.
- `sky_js/src/targets/mac/{click,type_text,scroll,set_value,press_key,paste,select_text,drag}.js` — each is one function: wrap in `withComputerUsePolicy(...)`, `getClient()`, call the matching client method (`e.click`, `e.typeText`, `e.setValue`, `e.pressKey`, `e.scroll`, `e.selectText`, `e.paste`, `e.drag`). No actuation logic.
- `sky_js/src/targets/mac/client.js` — `MacComputerUseClient`. `performAction` serializes an action union and sends `ComputerUseIPCAppPerformActionRequest` to the native service. Helper `h({elementIndex,x,y})` is where the rung is chosen: it emits `{elementID:{_0}}` when an index is present, else `{coordinate:{_0:[x,y]}}`. Actions: `click:{at,clickCount,mouseButton}`, `type:{_0:text}`, `setValue:{elementID,value}`, `pressKey:{_0:key}` (xdotool-style keysyms), `scroll:{at,direction,pages}`, `selectText:{elementID,text,prefix,suffix,selection}`, `drag:{from,to}`, `paste:{text,format}`.
- `SkyComputerUseService` (native, `nm -u` + `strings`) — the real actuator. Imports the AX rung: `_AXUIElementPerformAction`, `_AXUIElementSetAttributeValue`, `_AXUIElementCopyElementAtPosition` (coordinate -> element hit-test), `_AXValueCreate`, `_AXTextMarkerRangeCreate`. Action strings present: `AXPress`, `AXShowMenu`, `AXPick`, `AXConfirm`, `AXIncrement`/`AXDecrement`, `AXValue`, `AXSelectedTextRange`, `AXSelectedTextMarkerRange`. The pixel rung is NSEvent-based: `mouseEventWithType:location:modifierFlags:timestamp:windowNumber:context:eventNumber:clickCount:pressure:`, `eventWithCGEvent:`, plus `CGEventSource`/`CGEventType`/`CGEventFlags`/`CGScrollEventUnit`/`CGMouseButton`. Front-process control uses SkyLight/CGS: `_CGSMainConnectionID`, `ProcessSerialNumber`, `SetFrontProcessOptions`, `kCPSNotify*`. `_dlopen`/`_dlsym` are imported, so the private event-posting SPI (SLPS/SLEvent-class) is resolved at runtime rather than linked, which is why no `*PostEvent*` symbol appears statically. CONFIRMED that Codex synthesizes NSEvents carrying a `windowNumber`, exactly the window-routing the plain `CGEventPostToPid` path lacks.

### cua-driver
Same two rungs, in Rust, with the delivery details spelled out in code.

- `rust/crates/platform-macos/src/input/mod.rs` — states the model: "AX action (`element_index` path): `AXUIElementPerformAction`" vs "CGEvent / SkyLight (`x, y` path): ... Prefers `SLEventPostToPid` (SkyLight SPI) over the public `CGEventPostToPid`."
- `rust/crates/platform-macos/src/input/ax_actions.rs` — the AX rung. `perform_ax_action` -> `map_action` maps press/show_menu/pick/confirm/cancel/open to `AXPress`/`AXShowMenu`/`AXPick`/`AXConfirm`/`AXCancel`/`AXOpen`; `set_ax_value` writes `AXValue`; `focus_element` writes `AXFocused`; `select_nearest_container`/`capture_nearest_container_selection` fall back to an `AXSelected` write with read-back; `ensure_ax_action_enabled` refuses `AXEnabled=false` before dispatch.
- `rust/crates/platform-macos/src/input/mouse.rs` — the pixel rung and the decisive "CGEventPostToPid does not hit-test" evidence. `post_mouse_event` posts BOTH `skylight::post_to_pid` (SLEventPostToPid) AND `CGEvent::post_to_pid`, and stamps window-routing fields `f40`(pid)/`f51`/`f58`/`f91`/`f92`; the docstring explains that without a stamped window number "WindowServer falls back to a screen-location hit-test that skips non-key (backgrounded) windows." `post_mouse_moved_primer` sends a leading `mouseMoved` because "a backgrounded window that never received a move event has stale tracking state, so the synthetic mouseDown lands 'outside' the control." `click_at_xy`, `click_at_xy_chromium` (off-screen primer + user-activation gate), `click_at_xy_with_window_local`, `right_click_at_xy_*`, `middle_click_at_xy`, `drag_at_xy(_observed)`, `scroll_wheel_at_xy`. `click_at_xy_desktop*` posts to `CGEventTapLocation::HID` for the vision-driven desktop scope.
- `rust/crates/platform-macos/src/input/keyboard.rs` — `type_text` sets a Unicode string on a keycode-0 event with zeroed flags; `press_key`/`hotkey` via `key_name_to_code` (full virtual-keycode table); `post_keyboard_event` attaches the auth envelope (`attach=true`) for Chromium on macOS 14+; `hotkey_no_auth`/`press_key_bare_global` drop the envelope so `NSMenu` key equivalents fire; `press_key_global`/`type_text_physical_global` for HID/Screen-Sharing.
- `rust/crates/platform-macos/src/input/interactive.rs` — `InteractiveInputSession`, a stateful streaming input worker (batched `TextCommit`/`Key`/`Pointer`/`Scroll`) with no Codex analogue.
- Tool selection of rung, per tool: `tools/click.rs` `perform_ax_click` (AX) vs pixel branch; `button:"right"` -> `AXShowMenu`, `button:"middle"` -> pixel center-click; a background left pixel click first tries `element_at_screen_position` (AX hit-test) then routed events. `tools/type_text.rs` writes `kAXSelectedText` (`PATH_AX`) then falls back to CGEvent keystrokes (`PATH_KEY_EVENTS`); terminals skip AX. `tools/set_value.rs` `AXPopUpButton` child `AXPress` vs direct `AXValue` write vs `AXIncrement`/`AXDecrement` stepping vs Safari `do JavaScript`. `tools/press_key.rs` `dispatch_with_ax_oracle` (background auth post vs foreground bare HID). `tools/invoke_menu.rs` walks `AXMenuBar` and picks `AXPress`/`AXPick`/`AXShowMenu`/`AXOpen` per hop. `tools/scroll.rs` targeted CGEvent wheel vs focused-scroller keystrokes (PageDown/arrows). `tools/type_text_chars.rs`, `tools/double_click.rs`, `tools/right_click.rs`, `tools/hotkey.rs`.
- Not found in cua: any dedicated `select_text` tool or `paste` tool, and no `AXSelectedTextRange`/`AXSelectedTextMarkerRange` use (grep of `rust/crates` empty). Nearest module is `tools/type_text.rs` (`AXSelectedText` insert) and `tools/set_value.rs`.

### Delta
| Area | Match / who is ahead |
| --- | --- |
| AX action verbs (press/show_menu/pick/confirm/increment/decrement/value) | Match. Same AX symbols, same primary-AX policy. |
| Rung selection (index -> AX, x/y -> pixel) | Match. cua `click.rs`/`type_text.rs` mirror Codex `client.js` `h()`. |
| Pixel delivery robustness | cua ahead. Explicit SLEventPostToPid + public-post "belt+suspenders", `f40/f51/f58/f91/f92` stamping, `mouseMoved` primer, Chromium off-screen activation primer. Codex uses NSEvent+`windowNumber` and dynamic SkyLight, less visible. |
| Verification / effect tri-state | cua ahead. `verified`/`effect`/`suspected_noop`, AX read-back, `AXWebArea` web-content distrust, background-input gating. Codex returns void per `client.js`. |
| Streaming/interactive input | cua ahead. `interactive.rs` has no Codex counterpart. |
| `select_text` (in-field selection by matching text) | Codex ahead. Native uses `AXSelectedTextRange`/`AXSelectedTextMarkerRange`; cua has none. |
| `paste` (clipboard-format insert) | Codex ahead. cua has none. |
| `press_key` keysyms | Slight gap. Codex accepts xdotool syntax (`super+c`, `KP_0`); cua uses its own `key_name_to_code` names + `modifiers` array. |

### Recreate/port plan
Codex-like actuation already exists on cua for click/type/scroll/drag/keys/menu, so the work is filling two missing actuators and aligning the key vocabulary.

1. **Copy-verbatim**: lift `codex-corpus/mac/skills/macos-SKILL.md`'s "prefer element actions, fall back to coordinates" guidance into the cua system prompt / tool descriptions. cua's `click.rs` description already says this; keep wording aligned.
2. **native-patch (medium)**: add a `select_text` tool at `rust/crates/platform-macos/src/tools/select_text.rs` plus AX bindings for `AXSelectedTextRange` and `AXSelectedTextMarkerRange` in `crate::ax::bindings`. Reuse `type_text.rs`'s element resolution and `target_in_web_area` distrust. This is the one genuinely new native rung; model the field-match + prefix/suffix + selection_type contract on Codex `client.js` `selectText`.
3. **thin-port**: add a `paste` tool that writes the value+format to the clipboard and drives Cmd+V through the existing `hotkey`/`keyboard.rs` path (no new native code).
4. **thin-port**: extend `keyboard.rs::key_name_to_code` (or add a keysym translation layer) to accept Codex/xdotool keysyms (`super+c`, `Return`, `KP_0`) so prompts and traces transfer without rewriting key names.
5. **native-patch (optional parity)**: confirm cua's coordinate click already does the Codex NSEvent-`windowNumber` equivalent. It does, via `mouse.rs` window-routing field stamping and `click.rs`'s `element_at_screen_position` AX hit-test on the background left-click path; no change needed beyond documenting the equivalence.
